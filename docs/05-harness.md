# 05. 하네스: AI와 함께 만드는 방식

이 프로젝트는 서비스를 만드는 동시에 "AI 에이전트가 안정적으로 기여하는 환경"을 만드는 연습이다. 하네스란 에이전트가 읽는 문서, 실행하는 검증, 지켜야 하는 규칙의 묶음이다. 좋은 하네스는 사람이 매번 설명하지 않아도 에이전트가 같은 품질로 일하게 한다.

## 구성 요소

| 요소 | 위치 | 역할 |
|---|---|---|
| 진입 문서 | `CLAUDE.md` | 매 세션 자동 로드. 목적, 규칙, 명령, 문서 지도 |
| 결정 기록 | `docs/adr/` | 왜 이렇게 했는지. 에이전트가 되묻지 않게 한다 |
| 스펙 | `docs/specs/` | 기능 단위 계약. 구현 전에 쓴다 |
| 검증 루프 | `make check`, `.github/workflows/ci.yml` | 에이전트가 스스로 결과를 확인하는 수단 |
| 세션 훅 | `.claude/settings.json` (예정) | 웹 세션 시작 시 의존성 설치·DB 기동 |

## 작업 흐름

```
스펙 작성 → 테스트 작성 → 구현 → make check → 커밋 → (필요 시) ADR
```

1. **스펙**: `docs/specs/_template.md`를 복사해 `NN-기능명.md`로 만든다. 수용 기준은 "~하면 ~한다" 형태의 테스트 문장으로 쓴다. 에이전트에게 기능을 시킬 때는 이 파일을 가리키는 것으로 충분해야 한다.
2. **테스트 먼저**: 수용 기준 하나당 테스트 하나. 상태 전이는 API 레벨(`httpx` + 실제 Postgres)에서 검증한다.
3. **구현**: 스펙 밖의 일은 하지 않는다. 발견한 문제는 스펙 하단 "메모"에 남긴다.
4. **검증**: `make check`가 깨끗해야 한다. 실패를 스킵으로 덮지 않는다.
5. **커밋**: 하나의 스펙 = 하나 이상의 작은 커밋. 문서 변경은 코드와 같은 커밋에 넣는다.

## 에이전트에게 일을 시킬 때

- 좋은 요청: "`docs/specs/03-session-state-machine.md`를 구현해. 수용 기준 전부 테스트로 만들고 `make check` 통과시켜."
- 나쁜 요청: "타이머 만들어줘." (규칙·범위·검증이 전부 빠져 있다)
- 요청에 빠진 결정이 있으면 에이전트가 물어야 한다. 물어보지 않고 추측한 결정은 리뷰에서 지적한다.

## 리뷰 체크리스트

- [ ] 클라이언트가 보낸 시각·경과값이 집계에 쓰이지 않는가
- [ ] 상태 변경 트랜잭션에 `events` 삽입이 있는가
- [ ] 보상 상수를 코드에서 읽지 않는가
- [ ] 새 외부 의존성이 무료이고 `docs/04-deployment.md`에 기록됐는가
- [ ] 마이그레이션이 모델과 일치하는가
- [ ] 스펙의 수용 기준마다 테스트가 있는가
- [ ] 스킵된 테스트가 늘지 않았는가

## 성장 계획

| 단계 | 하네스 개선 |
|---|---|
| M1 | 스펙 3~4개를 실제로 돌려 템플릿을 다듬는다. SessionStart 훅 추가 |
| M2 | 반복되는 작업(마이그레이션 생성, 스펙 생성)을 `.claude/skills/`로 만든다 |
| M3 | PR마다 자동 코드 리뷰. 리뷰 체크리스트를 리뷰 프롬프트로 옮긴다 |
| M4 | 데이터 파이프라인용 별도 CLAUDE.md 섹션. dbt 테스트를 `make check`에 포함 |
