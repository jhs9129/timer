# ADR 0003. 상태 테이블 + append-only 이벤트 테이블 (outbox), 전체 이벤트 소싱은 하지 않는다

상태: accepted (2026-09-17)

## 맥락

운영자는 이 서비스의 데이터를 파이프라인 프로젝트로 확장하려 한다. 모든 사용자 행동이 시계열로 남아야 한다. 한편 팀은 한 명이고 무료 인스턴스 하나로 운영하므로 Kafka 같은 스트리밍 인프라는 쓸 수 없다.

## 결정

- 도메인 상태는 일반 테이블(`focus_sessions`, `coin_ledger` 등)에 유지한다.
- 상태를 바꾸는 모든 트랜잭션은 같은 트랜잭션 안에서 `events`에 한 행을 삽입한다. 애플리케이션 레이어의 `emit(event)` 헬퍼를 통해서만 삽입한다.
- `events`는 삭제·갱신하지 않는다. 파이프라인은 `ingested_at` 워터마크로 증분 추출한다(M4).
- 전체 이벤트 소싱(이벤트 재생으로 상태 복원)은 하지 않는다.

## 대안

- 전체 이벤트 소싱: 데이터는 가장 풍부하지만 조회 모델, 스냅샷, 재생 로직이 필요해 1인 프로젝트 범위를 넘는다.
- 별도 메시지 큐: 무료 구간에서 안정적으로 쓸 수 있는 것이 없고, 인스턴스 1개라 컨슈머를 따로 돌릴 수도 없다.
- DB 트리거로 이벤트 생성: 애플리케이션 의미(예: `cap_hit`)를 담기 어렵다.

## 결과

- 이벤트 누락은 코드 리뷰로 막는다. `CLAUDE.md` 규칙 2와 리뷰 체크리스트에 명시했다.
- `events` 테이블이 가장 빨리 자란다. Supabase 500MB 한도 전에 M4에서 파티션·내보내기를 구현해야 한다.
- 파이프라인은 Postgres에서 직접 읽는 배치 추출로 시작한다. 실시간이 필요해지면 그때 논의한다.
